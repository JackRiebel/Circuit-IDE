# CircuitCode Product Parity Master Checklist

Last audited: 2026-07-10

## Purpose

This is the canonical recovery and product-parity checklist for CircuitCode. The target is not a visual clone of Codex, ChatGPT, or Claude. The target is a trustworthy private AI workspace that reaches the same product class while supporting Circuit-specific models, agents, tools, connectors, and enterprise workflows.

Every item below has an objective completion gate. An item is not complete because code exists, a mockup looks correct, or one happy-path test passes. It is complete only when the implementation, automated verification, restart behavior, failure behavior, and user-facing outcome meet the stated acceptance criteria.

## Audit Method

This audit covered:

- The current Flutter macOS product under `circuit-ide/`.
- The legacy Python GUI, TUI, CLI, launcher, and CI paths still in the repository.
- Studio turn execution, intent routing, context, permissions, approvals, patches, commands, provider streaming, persistence, artifact generation, agent orchestration, MCP, settings, and release configuration.
- Current Studio source layout and screenshots supplied during product development.
- Current official Codex/ChatGPT and Claude documentation listed in [Reference Products](#reference-products).
- Current verification: `flutter analyze` passed and the focused Studio reliability, permission, task-engine, shell, and drawer test set passed on 2026-07-10.

Live visual capture of the running app was blocked by macOS Screen Recording permission during this audit. UI findings therefore use the current Flutter implementation plus the supplied screenshots. A later visual acceptance pass must capture fresh screenshots after that permission is granted.

## Product Definition Of Done

CircuitCode reaches the target product class when all of the following are true:

1. One canonical Studio runtime owns every user turn from prompt through final outcome.
2. A user can chat, research, plan, edit, verify, create artifacts, and continue without understanding internal prompts or tool protocols.
3. Tools run inside an enforceable workspace/process boundary, with granular request-scoped approvals and no plaintext secrets.
4. Projects, tasks, messages, artifacts, approvals, patches, commands, and outcomes survive restart without stale states.
5. Custom agents are first-class, testable, scoped products rather than hardcoded prompt variants.
6. Screenshots and supported images reach a multimodal model as pixels, not metadata claims.
7. The UI is outcome-first, accessible, keyboard-complete, responsive, and performant on long histories.
8. Flutter analyze, tests, visual tests, integration tests, security scans, signed build, and release smoke tests are required CI gates.
9. Production diagnostics explain failures without leaking prompts, credentials, environment variables, or customer data.
10. A new engineer or agent author can understand, run, extend, test, and release the app from maintained documentation.

## Non-Negotiable Engineering Rules

- **One owner per state:** Studio must not derive the same status from turn state, global chat state, task state, and UI fallbacks.
- **Guidance is not enforcement:** instruction files and prompts guide models; client policy and sandboxing enforce boundaries.
- **Outcome over instrumentation:** transcript content is for user decisions and results; diagnostics belong in Progress and trace views.
- **Typed boundaries:** provider events, tool calls, tool results, approvals, patches, artifacts, and agent handoffs use versioned typed envelopes.
- **Fail closed:** ambiguous mutation, network, Git, MCP, and secret access is denied or reviewed, never silently allowed.
- **No hidden internal prose:** model prompts, repair prompts, approval tokens, and orchestration instructions never become task titles or transcript messages.
- **Feature flags require contracts:** a disabled feature can be re-enabled only after it uses the same runtime, permissions, persistence, diagnostics, and tests as Studio.
- **Large passes must move the product:** each implementation pass must complete an end-to-end capability and remove obsolete paths. Cosmetic-only passes do not count toward parity.

## Priority Legend

- **P0:** security, data-loss, runtime ownership, or product-blocking trust issue.
- **P1:** required for a dependable daily-use product.
- **P2:** required for parity, scale, or professional polish.
- **P3:** valuable expansion after the core is stable.

## Ten Large Implementation Passes

Each pass must ship a meaningful end-to-end product improvement, remove obsolete code, add automated gates, and leave a fresh runnable Desktop build. A pass is not complete if it only adds models, placeholders, UI controls, or isolated unit tests.

### Pass 1 — Security And Release Truth

Complete `CC-SEC-001` through `CC-SEC-005`, `CC-REL-001` through `CC-REL-003`, and `CC-DOC-001`. Remove plaintext secrets, minimize child environments, establish the execution-boundary design, add Flutter CI, and produce a signed/notarization-ready build path.

### Pass 2 — One Canonical Runtime

Complete `CC-ARCH-001` through `CC-ARCH-005` and `CC-RUN-001`, `CC-RUN-002`, `CC-RUN-007`, `CC-RUN-008`. Quarantine legacy products and make Studio turn state the only truth with restart-safe transitions.

### Pass 3 — Codex-Grade Edit And Verify Loop

Complete `CC-RUN-003`, `CC-RUN-006`, `CC-RUN-009`, and `CC-EDIT-001` through `CC-EDIT-008`. Deliver one-task inspect-edit-approve-apply-verify-repair-summary behavior with crash-atomic patches and durable commands.

### Pass 4 — Projects, Worktrees, And Long-History Scale

Complete `CC-PROJ-001` through `CC-PROJ-005` and `CC-EDIT-004`. Deliver clear project/task semantics, worktree isolation, background task lifecycle, cleanup, and virtualized persistent history.

### Pass 5 — Context And Conversation Intelligence

Complete `CC-RUN-004`, `CC-RUN-005`, and `CC-CTX-001` through `CC-CTX-007`. Deliver evaluated retrieval, scoped instructions, accountable context, compaction, and collaborative broad-idea discovery.

### Pass 6 — Custom Agent And Plugin Platform

Complete `CC-AGENT-001` through `CC-AGENT-006` and `CC-PLUGIN-001` through `CC-PLUGIN-004`. Enable safe line-of-work agents, explicit/automatic routing, isolated subagents, connector consent, and required agent evals.

### Pass 7 — Multimodal And Research Workspace

Complete `CC-MM-001` through `CC-MM-003`, `CC-WEB-001`, `CC-WEB-002`, and `CC-BROWSER-001`. Deliver real screenshot vision, OCR provenance, cited research, and browser evidence artifacts.

### Pass 8 — Artifact Production Suite

Complete `CC-ART-001` through `CC-ART-007`. Consolidate renderer architecture, add templates/versioning/editing, and enforce visual/accessibility QA for customer deliverables.

### Pass 9 — Studio UX, Accessibility, And Performance

Complete `CC-UI-001` through `CC-UI-012`, `CC-A11Y-001` through `CC-A11Y-004`, and `CC-PERF-001` through `CC-PERF-005`. This is the enterprise polish pass after the runtime contracts are stable.

### Pass 10 — Production Proof

Complete `CC-OBS-001`, `CC-OBS-002`, `CC-EVAL-001` through `CC-EVAL-006`, and `CC-REL-004`, `CC-REL-005`, `CC-DOC-002` through `CC-DOC-004`. Run soak, red-team, visual, integration, clean-install, update, rollback, and support drills before declaring 1.0.

## How To Maintain This Checklist

1. Reference checklist IDs in commits and pull requests.
2. Do not check an item until its `Complete when` and `Verify` clauses are satisfied.
3. Add evidence links below the item when closing it: tests, screenshots, trace, release artifact, and ADR.
4. If implementation reveals a new requirement, add a new uniquely identified item rather than weakening an existing gate.
5. Re-score the maturity table after every large pass using current evidence.
6. Keep P0 work ahead of UI imitation. Trust, state correctness, and recoverability are part of the product experience.
